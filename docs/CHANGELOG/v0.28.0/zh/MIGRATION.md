# 迁移到 Plumb v0.28.0

## 重新渲染 lane

每个受治仓库的 guard 会动一行：`cargo test` 现在跑在 release 检查之后。方便时渲染并 land
即可——漂移只是 noted，不会 out of true，而没有任何声明的仓库，行为与今天完全一致。

## 声明是自愿的，而过窄的声明是唯一的风险

没有 `[workflow.hash]` 的仓库渲染如旧，也不会向锁问任何事。声明一个 key，它覆盖的步骤就只在
你点名的路径动过时才跑。

没有任何机制能抓住一份过窄的声明，因为只有产品知道自己的步骤读什么。过窄换来的是"跳过了一个
本会失败的步骤"。值得点名的陷阱：**一个把这个工具跑在这个仓库上的步骤，读的是整个仓库。**
在本仓库里 `cargo test` 断言 `plumb doctor` 判这棵树为真，所以它的输入是整棵树而不只是 crates；
而格式检查、lint 和 release 检查只读 Cargo 所读。

两条规则让声明保持诚实。输入相同的 key 应当合并，因为拆开什么也换不来。一个步骤是另一个的前置时
也应当合并，因为跳过包安装却去跑需要那些模块的检查，是任何声明都没有描述过的失败。

信任一份形状之前先跑 `plumb workflow status --since <rev>`。它把声明放回真实历史重放，
报出每个 key 本来会命中多少次。

## 锁座位不需要逐仓库配置

四项设置通过组织下发到每个受治仓库，lane 自己会点它们的名。新仓库声明 `[workflow.hash]`
就可以了。

## 在这一版成为装着的 stable 之前，什么都不会发生

lane 装的是已发布的工具，而已发布的工具按构造必然比装它的那条 lane 更旧。问与记都容忍自身失败，
所以由这一版渲染、由更旧的工具执行的 guard，行为与今天完全一致：全部照跑、什么都不记，
座位一直空着，直到装着的那个工具听得懂这个问题。
