# Plumb v0.28.0

无论动了什么，guard 都跑同一套检查。在本仓库，每一百个提交里有九十六个在为一次包安装、
一次格式检查、一次类型检查、一次测试和一次站点构建付账，而它们读的东西一个字都没变。
lane 不可能知道这件事，只有声明能说出哪些路径决定一个步骤的结论。

## 仓库声明每个步骤读什么

`[workflow.hash]` 按 key 指出哪些路径的记录字节决定该步骤。key 用一个斜杠分开它的 lane
与它自己的命名空间——lane 名是 Plumb 的封闭枚举，斜杠之后归产品自己划分，所以
`[workflow.hash.ship.cargo]` 下的嵌套读回来就是 `ship/cargo.rehearse`。

输入既覆盖这些路径下的字节，也覆盖声明本身，所以放宽一条声明会让它自己的 key 失效，
而不是留着一个过期的答案；它量的是 Git 记录下来的东西，不是工作座位里躺着的字节。

两个前缀让声明不必退化成通配。`key://` 把一个 key 的输入并进另一个，于是"读另外两个所读"
的步骤可以直说，而不必写 `*`。`suite://` 指向 Plumb 规则里的经典工具链清单，和机制必须遵守的
其他数值放在一起，于是产品声明的是意图而不是抄一份列表，而往套件里加一条路径是对 Plumb 的
改动。环、未知的 lane、key 或套件都会被拒。

## 锁说明 guard 是否已经见过这份输入

这份记录不能住在仓库里：只有跑绿过的运行才有资格写它，而一次运行不该写进它正在评判的那棵树。
一处座位装下全域所有仓库的锁，每个仓库在里面有自己的房间——否则两个产品用了同名的 key 就会
互相挤掉对方，谁都永远不命中。

房间由运行给出，所以没有运行命名座位的地方读不到也写不进锁。本该是一条"谁可以记录"的约定，
就此变成一件只有运行才做得到的事：在某人机器上跑绿的东西，再也不能拿给 guard 当作它已经看过。

## 渲染出的 guard 问一次，每条证明各自成步

一个步骤一次问齐所有声明的 key，每个 key 渲染成自己的具名步骤，只持有一个条件。跨多个步骤的
key 让它们共用那一个答案，并把锁记在最后一步——因为跳过包安装却去跑需要那些模块的类型检查，
会以任何声明都没有描述过的理由失败。

"某个声明的 key 的输入是否动过"与 `runner.os`、已解析的通道并列，成为渲染步骤可以持有的条件。
一条 lane 只写一次，却被其后每个提交读取，所以它所依据的 hash 是渲染期无法知道的——那正是
这份清单当初被写成封闭枚举而不是空集的理由。

条件写成"缺席即跑"。一个从未到达的答案、一个太旧而不认识这个问题的工具、一把谁也读不出的锁，
都会让输出为空，而空不是 `false`。反过来写的话，任何一次故障都会变成"guard 通过了它从未检查
过的东西"。

## `plumb workflow status`

`status` 打印每个 key 的摘要，以及每一条声明各自贡献了什么，所以短声明不丢信息；`--since`
把声明放回历史上重放，报出每个 key 本来会命中多少次。形状是这样调出来的，不是猜出来的：
本仓库写下的第一份声明就是错的，正是重放把它照了出来。

## 更小的几件事

`cargo test` 现在跑在 release 检查之后，好让"只读 Cargo 所读"的三条证明挨在一起。这一行在
每个受治仓库里都会移动，无论它有没有声明任何东西。

产品自己就是这个工具的仓库，会在自己的构建旁边装一份已发布的工具——因为"问一个步骤能不能跳过"
不该先把那个本来要跑的东西编译一遍。
