# 迁移到 Plumb v0.26.0

## 重新渲染 lane

guard lane 改了两处：它声明自己站在哪条发布线上，于是基准面在 CI 里也读得到，而不只是在
操作者手里；它把包存储座到源码之外，这是此前任何 guard 容器都没做过的。跑
`plumb lane --write` 并把结果落地。在那之前，渲染出的 lane 会照常报漂移，而发布拒绝在它
上面启动。

## 用这一版开发布线

早先的 Plumb 开出来的线不带基准面，于是 `doctor` 在那条线上报 out of true。用这一版切新线；
已经开着的线，要么对同一个版本再跑一次 `plumb stable prepare`（它只补记基准面，别的什么都
不动），要么在开它的那一版 Plumb 下走完。

`prepare` 与 `freeze` 现在在「上一个 stable 点还不是 `origin/main` 的祖先」时拒绝。如果有
一次发布已经发出去却从没 packport，先跑 `plumb stable packport --version <上一个版本>`。这
不是新增的工作，这是本来就该是最后一步、现在成了必须的那一步。

## 先跟踪，再封印

source seat 里有未跟踪叶子时，`plumb document` 不给任何提案。它要求的习惯 ——
先 `git add`，再 `plumb document` —— 本来就是正确的顺序，现在是被机制看着的顺序。

## 附件宽度

一个附件最多声明 Plumb 允许的包数：`cargo` 两个，`npm` 一个。声明得更多即 out of true，
而放宽这个许可是**改 Plumb**，不是产品做得出的声明。声明得比 Plumb 自己发布过的更宽，只
报 noted，不拒绝。

## 注册表里 `plumb 0.25.0` 那个洞

v0.25.0 发了 `plumb-macro`、跳过了 `plumb`，因为本版删掉的那个 skip 判定库没变。那个版本
在注册表里**不存在，也补不回来**：已发布的身份不可变，这个缺口是永久的。按 `0.25` 找过
却什么都没找到的人，看到的是一个真实的缺席。请依赖 `0.26.0` —— 它把两个都发出去。

## 本版之前记下的封印

封印的 `inputs` 以对象为键，而对象现在是附件、不再是包：`cargo/<crate>` 与
`npm/<package>` 变成 `cargo` 与 `npm`。于是早先的 baseline 什么都对不上，本版之后的第一次
发布会把每个对象都记成「在那个版本变过」。没有任何东西据此行动，所以除了证据的年龄之外
什么都没丢。

`[release.depends]` 的键用同一套名字。本域今天没有任何仓库声明过那张表。
