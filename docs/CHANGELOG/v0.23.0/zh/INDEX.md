# Plumb v0.23.0

## 受治理的 lane 由渲染得出，不再手写

每个仓库都手工维护自己的 workflow，也就各自漂移。guard 里从来没有一件事是只有
人才知道的：发布声明说明这个仓库是什么，仓库形状说明什么能证明它，运行中的
Plumb 带着模板。

`plumb lane` 推导出每一条受治理的 workflow，`--write` 落盘。漂移是与一次新渲染
的逐字节比较，而不是记录下来的印——Plumb 能重新生成的目标，不需要它本就推得出
来的证据。

渲染决定**有哪些 job**，而不只是每个 job 铺多宽。一个不声明二进制的产品，渲染出
的 lane 里根本没有 build、seal 与 smoke。原方案是让它们退化成空 matrix，但
Forgejo 不会跳过空 matrix 的 job：它根本不创建，于是所有下游永久阻塞。

漂移记为 noted 而非 out of true。危害只在发布时兑现，所以 `doctor` 报出来但仍然
绿，而 dispatch 会拒绝。一条从未渲染过的 lane 只得到那条提示——正是这一点让每个
仓库能按自己的节奏采纳。

## stable 发布自行推导它所提升的 exact

来源证明原先是两个 dispatch 参数，可它指向的那份印早已被校验了四件事，含 commit
完全相同。一个经得起四道校验的事实不是声明。

现在，站在冻结 commit 上的 exact tag 是候选集，权威面上**已发布的封印**是计数。
必须恰好一个：零个与多于一个都拒绝，不做启发式。拒绝落在 `stable freeze`，此时
还没有任何产物——于是失败的 exact 发布应当重跑，而不是接着打下一个候选。

## worker 是产品自己声明的介质

站点发布所用的 account 与 domain 原先来自 lane 变量，等于让 workflow 替产品决定
它出现在哪里。`[release.cfworker]` 声明两者，worker 因而进入投影面，和其他介质
一样领到自己的 job。exact 通道把版本停在各自的预览 URL 上，完全不碰流量；只有
stable 抵达声明的域名。

## 封印说明每个对象由什么构建

每个 ship 对象现在带一份输入摘要，覆盖其推导出的根下所有被跟踪的叶子，并计入渲染
lane 所钉住的工具链。每份摘要都盖上这些输入首次出现的版本号，所以一个自更早版本
起就没动过的对象会自己说出来。

## 投影会跳过没有动过的对象

「这个对象上次变化于哪个版本」这枚戳，本身就足以判定它不必再造一遍。现在每个
adaptor 都会读它：自更早版本起就没动过的 crate、包、chart 或 worker 会被点名，连
同那个版本一起报出，并且不再被投影。读者分得清跳过与遗漏，因为投影自己说了是哪
一种。

跳过是优化，永远不是门。读不到基准就全部投影并明说，而不是拒绝发布——所以失败的
方向永远是「发多了」，不会是「发了个假的」。

cargo 带来一处值得点明的后果：没动过的包保留它上次发布所用的版本，而所有对它的
依赖要求都指向那个版本。于是耦合的一对仍然被精确钉住，且不必要求一个谁也没构建过
的版本存在。
