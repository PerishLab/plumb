Inspect a regular JSON file within 4 MiB. The default --purpose data accepts a strict effective
wharf.release.snapshot/v1 world, canonical wharf.release.semantics record or
wharf.release.semantics.history/v1 checkpoint.
Check supported fields, bounded identities, references and internal consistency.
Data inspection makes no network request. Native run IDs, matching digests and valid data do not
authenticate an issuer, execution, baseline, canary or publication permission.
The JSON result explicitly retains authentication=false and publication=false.
Exit 0 means data is structurally valid, never that a release is admissible.
Exit 1 means refused; unreadable input is refused. Exit 3 means unknown required
world inputs, including a valid runtime claim without its actual resolution.
No release gate is activated.

With --purpose materials --product <name>, input is canonical adoption record
data. Independently verify the annotated stable, original resolved world and
complete distribution, exact full-source/Scene collection and bound native
adoption review. This shares the baseline reader's material verification and
lets a trusted producer check inputs before its issuer job completes. The
plumb.release.materials/v1 facts retain authentication=false and publication=false;
they do not authenticate the supplied record or replace its future native issuer.

With --purpose issuer --product <name>, input is a strict semantic object reference
containing url, sha256 and size. Fetch exact canonical bytes from that product's
fixed authority. Verify current protected Wharf requirements, main-history
ancestry and the exact native ship attempt, successful issuer job and successful
digest-bearing confirmation step. The surrounding run may still be in progress;
the issuer job must already be complete. A capture role cannot issue a record.
The plumb.release.origin/v1 facts authenticate record origin only.

With --purpose baseline --product <name>, input names an adoption record. Also
verify the actual annotated stable, complete original distribution and recorded
combinations, original resolved world, full source and immutable Scene collection,
and the exact current native adoption review. Missing historical plans or actual
resolved worlds remain unknown. The plumb.release.baseline/v1 facts describe a
retrospective initial adoption, never original historical release compliance.
An effective source tree differing from the archived source remains unknown
until its complete effective-source materials are supported; a tree hash alone
does not recover that material closure.

Materials, issuer and baseline modes make bounded remote reads and retain publication=false.
They establish no arbitrary program equivalence, execution, qualification, canary,
current activation or permission to publish. Issuer and baseline observations
require the matching trusted Wharf issuer; prepared material facts cannot
substitute for its confirmed record bytes.
Data mode refuses --product. Exit 1 is refusal; exit 3 is unknown required evidence.
With --purpose preparation --product <name>, input is a strict
wharf.release.semantics.world/v1 descriptor naming the exact native run, attempt,
control commit and job, plus public content-addressed world and material
references. The shared reader verifies protected-main producer history, the
completed successful semantic-world role and its unique confirmation step naming
both exact SHA256 values, then complete effective-source bytes and reconstructed
Git tree. Object, native-job and current-authority facts are rechecked.
The plumb.release.prepared/v1 report authenticates original preparation only;
it grants no current candidate freshness, semantic equality, baseline adoption,
qualification, activation or publication. Missing observations remain unknown.
Material facts summarize verified file count and identities; the library also
retains complete verified file data without expanding it into the CLI report.

With --purpose history --product <name>, input is a strict checkpoint reference.
It must equal the product's current fixed history discovery. Authenticate the
complete predecessor chain and each original native [retain] semantic history
job and unique [retain] history SHA256 step, exact repository, original adopted
stable and full baseline materials. No checkpoint may erase/retarget a reservation
or replace the original adoption. Discovery, objects, jobs and authority are
rechecked. Observation is bounded to 128 checkpoints and 16 MiB of checkpoint
bytes; exhaustion remains unknown. Retained history before inception stays
unknown, and a historical prefix cannot substitute for current discovery.

With --purpose retention --product <name>, input is canonical
wharf.release.semantics.history.request/v1 data with root, previous and native.
Verify the original adoption and exact current predecessor, collect the full
current marker inventory, retain earlier reservations even when tags disappeared,
and refuse changed marker targets. Return the next checkpoint as data with
authentication=false and publication=false. Missing discovery permits only an
initial data preparation; it proves neither physical absence nor historical
completeness. A writer still needs conditional create/update and unknown-write
recovery. Supplied native fields acquire no issuer authority from preparation.
History facts authenticate retained observations, never complete prior history,
family transitions, semantic equality, publication or activation. The matching
trusted producer and real formal consumption remain separate rollout obligations.


With --purpose family --product <name>, input names an adoption or canonical
wharf.release.semantics.transition/v1 record. Authenticate the complete historical
stable chain back to its original adoption, then independently reconstruct each
formal snapshot and original published world, retained marker reservations,
world-bound review and the shared semantic judgment. Caller-supplied Request
fields must exactly equal that derivation. Each Z preserves the original X.Y
anchor; a verified Y establishes its own new anchor without replacing the root.
Anchor continuity is derived only from preceding verified judgments, not claimed
as a new independently authenticated human review.
The reader requires complete formal distributions and refuses rolling anchors,
history rollback, retargeted markers or a mismatched minimum Y/Z result.
X transitions remain unknown until independent user-decision verification exists.
It repeats material, history, review, issuer and authority observations. Bounds
are 64 records and 8 MiB of record bytes; exhaustion remains unknown. Effective
source differing from archived source requires the bound complete source object;
its full bytes and reconstructed Git tree must match the original formal world.
The plumb.release.family/v1 facts authenticate this historical chain only, with
publication=false. They do not select the current latest stable, prove a
prospective candidate admissible, recover missing transitions or enable a gate.
A deployed matching transition issuer and actual formal consumption are still
required; valid supplied data is never substituted for native authentication.
Family facts explicitly report judgment=historical_reconciliation and
admission=unknown. The complete supplied Request and all cumulative
reservations remain bound and verified. For an already published historical
stable, the minimum Y/Z judgment uses the numeric prefix through that stable;
known intervening stables still prevent a skipped transition. This prefix is a
semantic comparison, never a reconstruction of the original reservation inventory.
Higher markers may already have existed then: original admission stays unknown.
These same Family facts remain explicit inside nomination and current selection.

With --purpose transition --product <name>, input is canonical transition record
data. Verify the prior authenticated family, the current fixed retained history,
current latest stable, complete published frame, exact world-bound review and
independently derived shared judgment. Retained history must cover every current
tag with its exact source; incomplete coverage remains unknown. Repeat the family, materials, review,
inventory, discovery and authority checks. Return plumb.release.transition.materials/v1
facts with authentication=false and publication=false. The preceding family is
authenticated; the derived family explicitly is not. Supplied native identity
acquires no authority, even when all material checks succeed. A trusted issuer
must independently bind its actual request/context and confirm exact public bytes.
This preparation admits no prospective release and activates no publication gate.
Current transition mode additionally assesses the complete reservation set;
historical reconciliation never bypasses current ordering or reservation conflicts.

With --purpose historical --product <name>, input is the same canonical
transition data. Independently verify the historical predecessor family, bound
retained checkpoint, original complete formal publication and exact review.
It can reconstruct a missing historical transition after newer stables exist,
using the actual retained checkpoint rather than today's reservation inventory.
It neither replaces a current head nor claims current latest-stable freshness.
The same materials report explicitly names freshness=historical; transition mode
names freshness=current. Both derived families retain authentication=false and
publication=false. Historical preparation cannot substitute for current release
admission. It does not reconstruct evidence absent from the retained history.

With --purpose choice --product <name>, input is an immutable selection record
reference. Authenticate its exact canonical wharf.release.semantics.family.selection/v1
bytes through the dedicated completed native [select] stable family role and
unique digest confirmation. This establishes issuer origin only, not that its
family is current or that its material or predecessor claims are valid.

With --purpose nomination --product <name>, input is canonical selection data.
Verify its complete authenticated family, exact original root, strict authenticated
selection predecessors on that same branch, increasing stable and sequence,
current retained history and complete tag inventory. A retained newer stable
cannot be ignored when its current tag disappears. Repeat material and freshness
checks. The plumb.release.selection.materials/v1 report retains authentication=false
and publication=false for the proposed selection. It proves no supplied native
identity, physical absence, conditional update, writer idleness or publication
permission. A trusted producer must bind its actual native identity, protected
predecessor bytes and conditional write, preserve unknown outcomes, and confirm
public bytes without a storage credential. Retain the first selection separately
at /v1/semantics/family/initial.json with create-only semantics. An established
inception must never be replaced or inferred absent from missing discovery.

With --purpose selected --product <name>, input is the expected original adoption
reference. Read the fixed /v1/semantics/family/latest.json selector, authenticate
its immutable selection record, complete predecessor chain and the separately
retained /v1/semantics/family/initial.json inception. The chain must end at that
exact first selection; a missing latest pointer cannot authorize reinitialization.
Independently reconstruct its family and retained history. Verify the expected original root,
current latest retained stable with its exact live source, complete current tag
inventory and current history extending the selected history. New RC reservations
may extend history without moving the stable selection. Repeat the selection,
materials, predecessor, history, inventory, discovery and protected authority
observations. Missing selectors or producers, exhausted 128-selection/16-MiB
predecessor bounds, missing latest stable, forks, rollback and moved inputs stop.
The plumb.release.family.current/v1 facts authenticate the selected current
metadata and family under that expected root; they admit no prospective candidate
and grant no publication or activation. The expected root must come from the
caller's trusted scope; supplying a root creates no scope authority. Formal
matching producer and consumer qualification remain required before activation.
