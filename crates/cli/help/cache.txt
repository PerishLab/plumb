Inspect and reclaim the Cargo build caches Guard keeps below PLUMB_HOME.

Guard compiles each repository into one bucket keyed by its canonical Git
common directory, so Members share their Integration's bucket and every
independent clone gets its own. Cargo never collects superseded units, so a
bucket grows with every dependency change it has seen.

Each successful Guard cargo action records the units it used: the units it
wrote, closed over Cargo's fingerprint graph. The most recently recorded units
are the bucket's working set; every other recorded unit is superseded.

Retention has three bounds:
- Idle time, 7 days. A bucket unused for 7 days, or whose Git common directory
  no longer exists, is reclaimed whole. In a live bucket, a unit or incremental
  session no run has used for 7 days is reclaimed, along with build outputs no
  fingerprint owns.
- Working set, 2x. A live bucket keeps superseded units, most recently used
  first, only while the bucket stays within twice its working set.
- Disk pressure. When the filesystem holding the caches has less than the
  reserve percent available, a live bucket keeps only its working set. If the
  filesystem is still below that line, whole live buckets are reclaimed, least
  recently used first, until it is back above the line or none is left. Guard
  never reclaims the bucket it is running in this way, and `reclaim` never
  reclaims the most recently used bucket.
Guard applies these to its own bucket after each action, and to every other
bucket at most once a day, or after every action under pressure.

The reserve is `reserve` in the [cache] section of PLUMB_HOME/plumb.toml, a
percentage from 0 to 100; PLUMB_GUARD_CACHE_RESERVE overrides it, and the
default is 30. The line is both where pressure starts and what it reclaims
toward, so it should sit above every gate that other tools enforce on the
same filesystem, with room for what they write. Concord's Artifact preflight,
for one, refuses unless the larger of a quarter of the filesystem and 1 GiB
stays available beyond the Artifact itself; the default 30 keeps 5% of the
filesystem above that gate for the Artifact and for what builds write between
sweeps. Raise the reserve when Artifacts are larger than that. Guard caches
can only restore the line when they are what holds the filesystem below it;
`status` says which.

Reclamation holds the bucket's lease without waiting. A held lease reports the
bucket active and leaves it alone. The lease file and the bucket's marker are
never removed. Guard acts only on a bucket that carries both its in-path marker
and its registry record below PLUMB_HOME/state. A bucket without a marker is
reported unknown; Guard leaves it alone, and only `reclaim --apply` removes its
content. A cache is acceleration, not evidence: a reclaimed unit is rebuilt by
the next Guard, and no proof depends on it.

PLUMB_GUARD_COMPILER_CACHE=sccache additionally routes Guard's Cargo actions
through an sccache disk cache at PLUMB_HOME/cache/compiler, with incremental
compilation off. It is off by default. Each Guard checks out a fresh path, and
sccache keys a workspace crate by its path, so only dependencies hit: it pays
when the Cargo bucket starts empty, as on a fresh CI runner, and rarely
locally, where the bucket usually holds them already. sccache bounds the directory at 2 GiB,
evicting least recently used entries. Enabled without sccache on PATH, Guard
refuses; any other value is refused. Enabling it changes the execution world,
so earlier proofs do not apply.

`status` reports every bucket with its working set, superseded bytes and the
current disk pressure: the line in bytes, how far below it the filesystem
is, and whether reclaiming Guard caches restores it or the rest is held
outside them. A bucket that pressure reclaims whole is marked. `reclaim`
previews the same targets, and `reclaim --apply` removes them and reports the
bytes reclaimed.
